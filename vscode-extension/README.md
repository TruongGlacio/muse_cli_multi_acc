# Muse cho VS Code (v0.8.19)

## Mới trong v0.8.19: mở extension vào ngay hội thoại mới nhất, vào chat là thấy tin cuối cùng

**Việc 1 — mở extension thì vào hội thoại tương tác mới nhất.** Trước đây bề mặt chat mới mở theo `savedCurrentSessionId` cũ trong globalState, còn danh sách giữ nguyên thứ tự tạo (tạo trước đứng trước) nên hội thoại vừa tương tác nằm tận dưới, user phải scroll xuống mới thấy. Từ bản này: khi mở sidebar/panel bình thường mà không có `initialSessionId` tường minh, session mở mặc định là session có `updatedAt` lớn nhất trong store; đường `initialSessionId` tường minh (mở tab mới cho một session cụ thể) giữ nguyên, không bị override. Danh sách gửi qua `postSessions()` nay sắp xếp mới nhất lên đầu theo `updatedAt` desc (tie-break `createdAt` desc rồi giữ thứ tự gốc); chỉ đổi thứ tự hiển thị, không đổi thứ tự lưu trong store, không đổi tổng số session hay logic lọc tài khoản. Lưới an toàn ở webview: sau khi render xong danh sách, nếu session đang mở nằm ngoài vùng nhìn thấy thì cuộn danh sách tới đúng item đó (`scrollIntoView`, block nearest). Store rỗng thì giữ nguyên trạng thái trống, không tự tạo session.

**Việc 2 — vừa vào đoạn chat thì cuộn xuống tin cuối cùng.** Trước đây handler `history` chỉ render từng bubble (mỗi lần append có cuộn, nhưng layout chưa ổn định ngay sau khi render nên vị trí cuối cùng không nằm ở tin cuối), còn handler `importedBanner` ép `scrollTop = 0` về đầu. Từ bản này: sau khi handler `history` render xong cả lô thì cuộn chốt xuống cuối một lần, rồi gọi lại sau 2 frame để chiều cao thực tế sau khi trình duyệt tính layout xong vẫn về đúng cuối; áp dụng cả lần mở panel đầu tiên lẫn mỗi lần chuyển hội thoại. Handler `importedBanner` bỏ việc ép về đầu: banner vẫn chèn ở đầu để user cuộn lên xem, nhưng điểm vào mặc định là tin cuối như mọi lần vào chat khác. Không cuộn thêm trong các handler khác (`streamDelta` đã tự cuộn, `sessions` chỉ render danh sách) để tránh giật cuộn khi đang chat.

## Mới trong v0.8.18: model tự lấy ảnh và khung hình video trong workspace (không cần đính kèm tay)

**Vấn đề cũ.** File text/code thì model đã tự lấy được qua vòng lặp tool (`read_file`/`read_files`/`search_files`/`list_files`), nhưng file media thì không: model không có tool nào để lấy ảnh hay video trong workspace, nên user vẫn phải đính kèm tay. Đính kèm tay thì ảnh gửi dạng ảnh, còn video chỉ trích 1 khung ở giây 1 bằng ffmpeg (không có ffmpeg thì chỉ gửi ghi chú).

**2 tool đọc-only mới.** `read_image {path}` đọc 1 file ảnh trong workspace và gửi ảnh kèm message kết quả của chính call đó; chỉ nhận `.png`/`.jpg`/`.jpeg`/`.webp`/`.gif`, tối đa 20 MiB/ảnh, sai định dạng, rỗng, quá lớn hoặc ngoài workspace đều trả lỗi text rõ ràng, không bịa ảnh. `read_video_frames {path, times?}` trích khung hình video bằng ffmpeg theo đúng mẫu đính kèm tay (mỗi mốc một file tạm, dọn sau khi đọc); `times` mặc định `[1]`, tối đa 4 mốc, mỗi mốc >= 0, sai thì trả lỗi text; mỗi khung thành một ảnh kèm cùng message kết quả. Không có ffmpeg hoặc trích hỏng hết thì chỉ trả ghi chú thành thật, tuyệt đối không bịa khung hình. Text kết quả luôn ghi rõ đây chỉ là khung hình mẫu, không phải toàn bộ video. Cả 2 tool đều nằm trong nhóm đọc-only nên không hỏi duyệt modal (giống `read_file`), vẫn bị chặn ngoài workspace, và khi `muse.localTools=false` thì bị từ chối toàn bộ như mọi tool khác. System prompt dặn model chỉ gọi 2 tool này khi user yêu cầu kiểm tra media trong workspace, không tự quét media toàn workspace khi chưa được yêu cầu.

**Đường gửi ảnh tái dùng, không làm mới.** Vòng lặp chat nay tổng quát hóa cơ chế ảnh vốn chỉ dành cho screenshot `computer_*`: tool nào trả về ảnh thì message kết quả của call đó kèm đúng các ảnh tương ứng, tool khác vẫn text thuần, hành vi `computer_*` giữ nguyên. Phía gateway KHÔNG phải sửa gì: `Prompt.Flatten` đã gom `image_url` từ mọi message (kể cả message kết quả tool), handler chat nạp ảnh qua `LoadImageRefs` và `BrowserDriver.Attach` đưa lên web, kèm dedup `ImageBatchId`/`ImageHash` sẵn có; ảnh kết quả tool không có `attachment_id` nên không bị dedup bỏ qua, và các lượt sau chỉ attach thêm ảnh mới vượt quá số lượng đã attach.

**Giới hạn, nói thẳng.** Video gốc không bao giờ được gửi lên web qua đường này, chỉ có khung hình mẫu; muốn xem toàn bộ video thì vẫn phải mở file gốc trên máy. Ảnh quá 20 MiB, video không có ffmpeg, hoặc media ngoài workspace đều không gửi được và model chỉ nhận ghi chú lỗi.

## Mới trong v0.8.16: log đúng prompt gateway gửi lên muse.ai (chẩn đoán câu từ chối của model web)

**Vì sao cần.** Khi model web trả câu từ chối kiểu "Xin lỗi, tôi không thể giúp bạn xử lý yêu cầu này ngay được...", gateway trước đây chỉ chuyển nguyên văn câu đó về khung chat mà không cho thấy nó đã gửi gì lên web, nên không đối chiếu được nguyên nhân. Từ bản này, mỗi lượt chat gửi lên web đều để lại một khối log `web_prompt` trong Output > Muse Gateway, ghi đúng chuỗi cuối cùng được điền vào ô chat trên trang (không phải bản thô trước khi gộp).

**Đọc log như thế nào.** Mỗi lượt có một dòng header dạng `[local] web_prompt account=<id> mode=<normal|local|openai-tools> model=<model> chars=<số ký tự prompt> turns=<số lượt tin> thread=<new|reused> images=<số ảnh đính kèm> file=<đường dẫn file hoặc ->`, tiếp theo là `web_prompt_begin`, toàn bộ nội dung prompt, rồi `web_prompt_end`. Chế độ `normal` là chat thường (prompt đã gộp bằng `Prompt.Flatten` kèm chỉ thị cuối "Continue the conversation above... Output only the reply"); `local` là luồng extension local-tools (prompt là kế hoạch JSON, kèm dòng header transport `MUSE_LOCAL_REQUEST_ID:` ở đầu — đó là metadata vận chuyển, model được dặn không echo lại); `openai-tools` là luồng Kilo tools ở 0.8.15 (prompt đã gộp cộng catalog tool). `thread=reused` nghĩa là nối tiếp thread web cũ, `new` là mở thread mới. `chars` đếm theo độ dài chuỗi (UTF-16) như dòng `local_reply_complete` đếm reply, để đối chiếu hai đầu.

**Prompt dài và file toàn văn.** Prompt dài hơn 20000 ký tự thì Output chỉ nhận preview: 10000 ký tự đầu + dòng `web_prompt_truncated chars=<tổng> shown=<số ký tự preview> file=<đường dẫn>` + 5000 ký tự cuối (cắt an toàn, không cắt đôi emoji/ký tự ngoài BMP ở biên). Toàn văn prompt dài được ghi ra file local dưới thư mục dữ liệu của gateway, ví dụ `<thư mục dữ liệu gateway>/prompts/web_prompt_20261102_094700_abcd1234.txt` (trên máy user thường là `globalStorage/thanhtaiinguyen.muse-vscode/gateway/prompts/`), và header ghi rõ đường dẫn đó để mở ra xem đúng toàn văn. Prompt ngắn hơn hoặc bằng 20000 ký tự thì in toàn bộ vào Output và không ghi file (`file=-`). Nếu ghi file lỗi (ví dụ hết ổ đĩa) thì lượt chat vẫn chạy bình thường, header ghi `file=write_failed` và preview vẫn được in.

**Chống flood và riêng tư (đọc kỹ).** Đây là ngoại lệ có chủ ý so với quy tắc "log chỉ đếm số lượng" của các dòng `[local]` khác, theo yêu cầu tường minh của user: nội dung prompt là dữ liệu của chính user trên chính máy user, chỉ nằm ở Output local và file local nói trên, không gửi đi đâu. Để không tràn ring buffer 1000 dòng và panel Nhật ký, phía extension tách riêng các dòng nội dung prompt (tiền tố `web_prompt_body `) chỉ ra Output, còn ring buffer/panel chỉ nhận header, dòng `web_prompt_begin`/`web_prompt_end` và dòng `web_prompt_truncated`. Không log nội dung reply (reply đã hiện trong khung chat và đã có dòng `local_reply_complete` đếm ký tự), không log key, cookie, header xác thực hay token dưới bất kỳ hình thức nào. Lưu ý: mẫu trông giống key (dạng `token: ...`, `api_key: ...`) trong nội dung prompt vẫn bị bộ redact log sẵn có che đi như mọi dòng log khác, và dòng trống trong prompt vẫn được giữ nguyên để không lệch cấu trúc preview. File prompt có thể chứa nội dung nhạy cảm của chính bạn — đừng gửi nguyên file log cho người khác nếu trong đó có nội dung nhạy cảm.

**Giới hạn, nói thẳng.** Log này chỉ cho thấy gateway gửi gì, chưa tự kết luận được nguyên nhân từ chối: sau khi cài 0.8.16 và tái hiện đúng lỗi từ chối, mới đối chiếu được prompt cụ thể với câu từ chối đó. Hai đường `Send` khác trong code thuộc luồng tạo ảnh/video (gửi prompt tạo media và câu nhắc đính kèm file) không thuộc phạm vi log chat này nên không ghi `web_prompt`.

## Mới trong v0.8.15: lớp dịch tool OpenAI để Kilo Code code thật qua gateway

**Vấn đề cũ.** Gateway đã có endpoint `POST /v1/chat/completions` chuẩn OpenAI, nhưng handler chat chỉ đọc `model`, `messages`, `user`, `account_id`, `stream` và cờ riêng `_muse_local_tools`; nó không đọc trường `tools`/`tool_choice`/`parallel_tool_calls` của client, mà gộp toàn bộ tin nhắn thành text bằng `Prompt.Flatten` rồi gửi lên agent web muse.ai. `Flatten` còn thêm chỉ thị cuối bắt agent chỉ trả lời bằng chữ. Vì vậy client OpenAI như Kilo Code không bao giờ nhận được `tool_calls`, nên không sửa file hay chạy lệnh được qua gateway — chỉ hỏi đáp bằng chữ.

**Cách làm (chỉ dịch, không tự thực thi).** Khi request chat completions có `tools` là mảng non-empty VÀ `_muse_local_tools=false` thì gateway vào chế độ "openai-tools": (a) render danh mục tool từ `tools` thành đoạn hướng dẫn append vào prompt đã gộp, yêu cầu agent web khi cần hành động thì CHỈ trả đúng một khối JSON dạng `{"tool_calls":[{"name":"...","arguments":{...}}]}` và không kèm text khác, khi không cần hành động thì trả text thường; (b) parse reply của agent web (ưu tiên fence ```json, fallback JSON trần chứa khóa `tool_calls`), kiểm tra chặt từng call — tên phải trùng đúng một tool đã khai báo trong chính request đó và arguments phải parse được thành JSON object (arguments trả về cho client luôn ở dạng chuỗi JSON đúng chuẩn OpenAI) — call nào không đạt thì toàn bộ reply được coi là text thường, không bao giờ trả tool_call sai tên hoặc arguments vỡ sang client; (c) tôn trọng `tool_choice` (`none` thì không bao giờ trả call, tên function cụ thể thì chỉ trả call của tool đó, `auto`/mặc định thì trả các call hợp lệ) và `parallel_tool_calls=false` (chỉ trả tối đa 1 call hợp lệ đầu tiên); (d) trả đúng chuẩn OpenAI: không stream thì `choices[0].message` gồm `role` assistant, `content` rỗng khi có call, `tool_calls` dạng `[{id, type:"function", function:{name, arguments}}]` với id dạng `call_` + 24 ký tự hex, `finish_reason` là `tool_calls` khi có call và `stop` khi không; có stream thì gateway buffer toàn bộ reply web rồi phát lại thành SSE đúng chuẩn (delta `tool_calls` với id/tên ở chunk đầu, arguments ở chunk sau, rồi delta `finish_reason` tool_calls, cuối cùng `[DONE]`), không bao giờ trả JSON non-stream khi client yêu cầu stream. Lượt tool-result cũng được xử lý: `Flatten` nay render tin nhắn `role:"tool"` thành block "Tool result for <tên tool suy từ tool_call_id, nếu không suy được thì chính tool_call_id>" kèm nội dung, và tin nhắn assistant có `tool_calls` được render kèm dòng "[Assistant called tool <name> with arguments ...]" để agent web biết mình đã gọi gì ở lượt trước. Logic dịch nằm ở file mới `src/Muse2Api/OpenAiTools.cs` dưới dạng hàm thuần dễ test, không nhét hết vào `Endpoints.cs`.

**An toàn và ranh giới (đọc kỹ).** Ở chế độ này gateway KHÔNG tự thực thi bất kỳ thao tác file/lệnh nào trên máy user. Nó chỉ dịch qua lại; tool vẫn do chính Kilo thực thi trong VS Code của user dưới cơ chế duyệt của Kilo. Luồng `_muse_local_tools=true` của extension Muse không bị đụng tới: chế độ tools chỉ kích hoạt khi `_muse_local_tools=false`, và luồng extension vẫn dùng `Prompt.ForLocalExecutor` với giao thức kế hoạch JSON riêng của nó như trước.

**Cách bật với Kilo Code.** Trong Kilo Code chọn provider OpenAI Compatible (Custom provider), điền Base URL `http://127.0.0.1:18610/v1` (không thêm `/chat/completions`), API Key là key bạn đã tự đặt trong setting `muse.apiKey` của extension Muse rồi khởi động lại gateway (key tự sinh của extension nằm trong SecretStorage nên không lấy ra để dán sang Kilo được), Model là `muse-chat`, và nếu Kilo có cờ bật tool calling cho model custom thì phải bật cờ đó cho model này. Extension Muse phải đang mở trong cùng VS Code để gateway kèm theo chạy trên cổng 18610.

**Giới hạn còn lại, nói thẳng.** (1) Rủi ro chính là độ tin cậy của việc agent web tự phát JSON tool-call: nó không phải model function-calling chuẩn, có thể phát JSON sai định dạng hoặc bịa tham số; đã giảm thiểu bằng validation chặt + fallback về text, nhưng không loại bỏ được — Kilo vẫn phải duyệt từng thao tác như mọi tool call khác. (2) Mỗi bước tool của Kilo là một vòng browser round-trip lên muse.ai nên chậm hơn model API native. (3) Ở chế độ tools, stream bị buffer toàn bộ reply rồi mới phát SSE, nên không có delta trực tiếp cho tới khi agent web trả xong. (4) Pool mặc định 1 tài khoản nên Kilo và khung chat Muse dùng chung một tài khoản sẽ xếp hàng chờ nhau. (5) Chưa kiểm chứng trên Kilo Code thật với tài khoản thật — mới kiểm chứng bằng driver mock (xem mục kiểm chứng trong commit 0.8.15): cần user thử thật trên Kilo để biết agent web phát JSON ổn định tới mức nào.

## Mới trong v0.8.14: vá triệt để lỗi mất logo danh sách extension

**Nguyên nhân gốc (không phải artwork hỏng).** Logo danh sách extension/Marketplace là `images/icon.png` (PNG 128x128, package.json trường `"icon"` trỏ tới nó). Quy trình snapshot-push của repo chỉ chở file text UTF-8 nên file binary này không bao giờ lên được GitHub: nhánh `vscode_extention` tại head 0.8.12 có `media/icon.svg` nhưng không có `images/icon.png`. Hệ quả: bất kỳ ai build extension từ source trên GitHub đều đóng gói ra vsix thiếu logo danh sách extension, VS Code hiện icon mặc định, tức là "mất logo". Logo thanh activity bar (`media/icon.svg`, vẽ bằng path, không dùng thẻ `<text>` từ 0.8.0) là file text nên đã có trên GitHub từ trước và không bị lỗi này — hai logo này khác nhau, đừng nhầm.

**Cách vá (giữ nguyên artwork, không vẽ lại, không đổi màu/hình).** Thêm file text `images/icon.png.base64` chứa đúng base64 của `images/icon.png` hiện tại (2186 byte), để snapshot-push chở được; và script Node thuần `scripts/ensure-extension-icon.js` (chỉ dùng built-in của Node, không phụ thuộc mới): nếu `images/icon.png` thiếu hoặc nội dung khác với base64 đã giải mã thì ghi lại từ base64, sau đó kiểm tra file tồn tại, đúng chữ ký PNG và IHDR 128x128, và package.json trường `icon` vẫn trỏ tới nó. Nếu file base64 thiếu hoặc không khôi phục được thì script thoát mã lỗi khác 0 kèm thông báo rõ ràng — đóng gói phải dừng lại, không được lén ra vsix thiếu logo. Từ nay không bao giờ đóng gói ra vsix thiếu logo nữa (fail-fast), kể cả khi build từ source chỉ gồm file text trên GitHub.

**Quy tắc đóng gói bắt buộc (đọc trước mọi lần vsce package).** Trước mọi lần `vsce package` đều phải chạy `node scripts/ensure-extension-icon.js` từ thư mục `vscode-extension`. ### Lỗi 502: không timeout, không vứt câu trả lời (0.8.12)

**Trade-off đọc trước, ngay đầu mục này: từ 0.8.12 gateway KHÔNG tự cắt câu trả lời nữa, chỉ nút Dừng mới dừng. Nếu web kẹt thật thì gateway sẽ chờ mãi cho tới khi bạn bấm Dừng. Đây là hành vi theo đúng yêu cầu của user ngày 01/11, không phải lỗi treo mới.** Trước đây lỗi 502 xảy ra với cả câu chat ngắn đơn giản (ví dụ chỉ bảo phân tích 1 video đính kèm), không chỉ câu dài hay có tool, vì vòng trả lời chat bị cắt bởi timeout: 300 giây tổng, 45 giây chưa có token đầu tiên, 90 giây không tiến triển DOM, hoặc gợi ý kẹt sau 15 giây. Bản này gỡ toàn bộ các lần ném lỗi theo thời gian khỏi vòng trả lời chat trong `BrowserDriver.ChatStream`: ném Timeout khi quá `ChatTimeout`, ném `ResponseUnavailable` khi quá `FirstTokenTimeout`, ném `ResponseUnavailable` khi quá `ChatIdleTimeout`, và ném Timeout khi đuôi trang chứa gợi ý kẹt sau 15 giây. Chỉ giữ lại đường dừng do hủy: `req.Cancel` (bạn bấm Dừng ở extension, AbortSignal truyền xuống) vẫn kết thúc vòng lặp ngay, không ném 502, hội thoại được giữ nguyên qua khối finally hiện tại (lưu với trạng thái chưa hoàn tất, tab đánh dấu Stale). Các trường timeout vẫn còn trong `Settings.cs` vì code khác (media, profile) có thể còn dùng; chỉ `ChatStream` không còn dùng chúng để cắt câu trả lời. Bong bóng lỗi 502 của extension giữ nguyên dạng cũ cho các nguyên nhân khác (ví dụ hết hạn, lỗi driver) nếu sau này vẫn xảy ra, không sửa trong bản này.

**Không gắn được vẫn trả tin nhắn thô, không vứt câu trả lời dài.** Trường hợp web đã dừng nhưng gateway không gắn được phản hồi vào đúng yêu cầu đã gửi (cơ chế gắn theo mã yêu cầu và khóa tin nhắn người dùng hay hỏng khi DOM thay đổi): từ bản này, sau khi web dừng tạo và hết grace 15 giây, đường fallback ở chế độ LocalTools BỎ các điều kiện gắn cũ (`localReplyBound=true`, userKey khác baseline, `replyAfterUser=true`). Điều kiện duy nhất để trả là `lastText` khác rỗng, khác baseline, và ổn định qua 4 poll (0,6 giây) như đường thường để khỏi trả chữ đang render dở. Gateway trả `lastText` nguyên văn dưới dạng tin nhắn thô của assistant qua SSE như phản hồi thường, không cắt, không tóm tắt, không tự sửa JSON bên trong, và ghi một dòng chẩn đoán `local_reply_raw_fallback` gồm elapsed, gotFirst, bound, số ký tự và lý do kết thúc, không ghi nội dung tin nhắn. Khi vòng chat kết thúc do bạn bấm Dừng thì ghi một dòng `chat_ended` tương tự với lý do `user_stop`. Nếu `lastText` rỗng hoặc bằng baseline thì không ném 502, tiếp tục poll chờ tới khi bạn bấm Dừng. **An toàn với JSON tool dở dang:** việc trả thô không đồng nghĩa với thực thi tool từ JSON vỡ. `parseToolCalls` của extension chỉ tạo `__parse_error__` cho JSON vỡ và vòng lặp agent không thực thi lô nào có lỗi đó (gửi yêu cầu sửa định dạng, quá 3 lần thì dừng và báo rõ là không thực thi thao tác nào từ các phản hồi lỗi); fence JSON không đóng hoặc không chứa từ khóa tool thì trả về rỗng và hiện như text thường, không thực thi. JSON tool hợp lệ hoàn chỉnh trong text thô thì thực thi như bình thường. Vì vậy không vì sợ JSON vỡ mà quay lại vứt toàn bộ tin nhắn. **Phạm vi áp dụng:** phân tích video đính kèm (khung hình ở giây thứ 1 cộng text mô tả) vẫn đi qua cùng vòng chat này nên cũng hưởng luật không timeout và fallback thô như mọi câu chat khác.

(c) Chống nhập lại sau đồng bộ: khi xóa session có `threadUrl`, URL đó được ghi vào tombstone (lưu `globalState`, khóa riêng `muse.deletedThreadUrls`, chỉ chứa threadUrl đã bị user xóa); luồng đồng bộ bỏ qua mọi URL trong tombstone và báo rõ số hội thoại đã xóa nên không nhập lại; lệnh palette "Muse: Cho phép nhập lại các hội thoại đã xóa" xóa toàn bộ tombstone, lần đồng bộ sau mới nhập lại được. Session không có threadUrl thì không cần tombstone. Xóa session theo tài khoản (Xóa hoàn toàn) cũng ghi tombstone cho các thread của tài khoản đó. (d) Chỉ còn 1 session thì nay cho danh sách về rỗng an toàn thay vì làm trống + đổi tên thành "Hội thoại 1" như cũ (hành vi cũ khiến user tưởng xóa không được): `currentSession()` trả null khi rỗng, UI hiện trạng thái trống với nút Hội thoại mới, gửi tin khi rỗng thì tự tạo session mới rồi mới gửi; `SessionStore` không tự tạo session khi tải danh sách rỗng (chỉ tạo từ lịch sử legacy còn tin nhắn thật). Sau khi xóa, session biến mất khỏi cột trái và tab panel, và không quay lại sau khi khởi động lại VS Code (đã gọi save/persist + notify). **KHÔNG xóa thread trên web muse.ai** (đồng bộ mức 1 không có tính năng xóa web, gateway không có API xóa thread): hộp xác nhận xóa session có threadUrl nói rõ xóa ở đây chỉ xóa trong extension + mapping gateway, thread gốc vẫn còn trên web trừ khi user xóa tay trên web; và nhờ tombstone nên đồng bộ sẽ không tự nhập lại thread đó nữa.
3. **Việc 3 — Tạo hội thoại mới phải chọn tài khoản.** Nguyên nhân cũ: `newSession()` tạo session không có accountId rồi chỉ gán khi pool có đúng 1 tài khoản, nên user nhiều tài khoản mãi thấy "Chưa xác định tài khoản"; gate khi session không có accountId thì cho gửi đi, gateway tự chọn tài khoản theo pool, extension không bao giờ biết tài khoản thật đã dùng. Nay: pool 1 tài khoản thì gán luôn không hỏi; pool từ 2 tài khoản thì hiện QuickPick với nhãn Email → Username → Label kèm mã `acc_` và trạng thái (như syncFromWeb), chọn xong mới tạo session gắn accountId đó, hủy QuickPick thì không tạo session; pool 0 tài khoản thì không tạo session, báo rõ và mở panel Cài đặt. Áp dụng cho cả nút Hội thoại mới trong cột trái, lệnh palette "Muse: Hội thoại mới" và nút tạo trong tab panel (cùng một hàm, không đường tắt). Tài khoản đã chọn nay thực sự được dùng khi gửi tin: extension gửi thêm `account_id` trong body `/v1/chat/completions` (gateway cũ bỏ qua trường lạ, gateway mới đọc nó); gateway khi nhận `account_id` thì dùng đúng tài khoản đó qua `AcquirePinnedAsync` — tài khoản không còn trong pool, đang tắt, Invalid hoặc đang cooling thì trả lỗi nêu rõ id tài khoản đó, không tự ý chọn tài khoản khác rồi im lặng, và lỗi của tài khoản đã ép cũng không failover sang tài khoản khác. Session đã có accountId mà tài khoản logout/Invalid/cooling/disabled thì gate cũ vẫn chặn như trước. Backfill cho session đã chat nhưng chưa có accountId: endpoint mới `GET /admin/conversations/by-hint/{hint}` (RequireAdmin) đọc file mapping của hint, lấy `Entry.Account` (là hash) đối chiếu với hash của từng tài khoản trong pool, trả Public của tài khoản đó, không tìm thấy hoặc tài khoản không còn trong pool thì 404, không trả hash ra ngoài; extension gọi endpoint này khi làm mới tài khoản, khi chuyển session và sau lần chat đầu tiên thành công của session chưa có accountId, rồi lưu lại + làm mới danh sách để dòng tài khoản hiện đúng tài khoản thật đã dùng; lỗi/404 thì giữ nguyên "Chưa xác định", không chặn chat. **Giới hạn backfill: chỉ làm được khi mapping còn và tài khoản còn trong pool; session đã chat từ bản rất cũ mà mapping đã mất thì không backfill được, user cần tạo hội thoại mới (bản này không có tính năng sửa tài khoản của session cũ).**
4. **Việc 4 — Chat thuần, không quét workspace khi chỉ chào hỏi.** Nguyên nhân cũ: extension gửi `_muse_local_tools: true` cứng trong mọi request và system prompt nói agent là trợ lý lập trình với đầy đủ tool, nên ngay cả câu chào agent cũng quét workspace để "tìm hiểu ngữ cảnh"; tool chỉ đọc (list_files, read_file, read_files, search_files, git_status, git_diff) lại chạy không cần duyệt modal, và kết quả tool được đưa trở lại cho model ở lượt tiếp theo — nên tên file/thư mục (lần user báo: tới 500 entry, hơn 43.000 ký tự) thực sự đã gửi lên muse.ai. Nay: (a) system prompt thêm quy tắc ngay đầu, bằng tiếng Việt: chỉ dùng tool cục bộ khi user yêu cầu làm việc với file/code trong workspace; với câu chào hỏi, câu hỏi chung, trò chuyện thông thường thì trả lời trực tiếp, không quét workspace trước, không gọi tool để "tìm hiểu ngữ cảnh" khi user chưa yêu cầu. Lưu ý trung thực: khi setting bật thì việc agent có còn tự quét hay không phụ thuộc model tuân thủ quy tắc prompt này, không đảm bảo 100% bằng code. (b) Chế độ chat thuần: setting mới `muse.localTools` (boolean, mặc định true — giữ nguyên hành vi hiện tại, không đổi mặc định im lặng); khi = false thì extension gửi `_muse_local_tools: false` (gửi rõ false, không bỏ trường), không đưa hướng dẫn tool cục bộ vào system prompt (dùng prompt chat thuần riêng, không chứa tool), và nếu agent vẫn trả JSON tool thì extension từ chối thực thi toàn bộ lô và báo rõ tool đang tắt (có phòng thủ thêm ở đầu hàm execute, kể cả tool máy tính) — chế độ này đảm bảo bằng code là không còn tool nào chạy, không còn dữ liệu workspace nào gửi lên model qua tool. Lệnh palette "Muse: Bật/Tắt tool cục bộ" đổi setting nhanh mà không cần mở Settings; khi tắt thì agent không đọc/sửa/chạy gì trong workspace được, chỉ trò chuyện. (c) Giới hạn dữ liệu tool gửi ngược lên model: `list_files` nay tôn trọng `limit`/`offset` agent gửi (mặc định limit 50 khi không gửi, tối đa 500) và cắt chuỗi JSON kết quả tối đa 8000 ký tự kèm ghi chú "đã cắt, dùng limit/offset để xem tiếp" khi vượt quá (kể cả khi còn entry thì ghi chú "còn tiếp, dùng limit/offset để xem tiếp"). (d) Giữ nguyên việc tool chỉ đọc không hỏi duyệt modal (không làm hỏng luồng code), nhưng ghi rõ: **kết quả tool chỉ đọc vẫn được gửi ngược lên model theo đúng vòng lặp agent — muốn không có dữ liệu workspace nào đi lên thì dùng chế độ chat thuần ở trên.**

## Giới hạn thật của đồng bộ từ web (đọc trước khi dùng v0.6.0)

- Danh sách có thể thiếu nếu sidebar muse.ai tải lười/thu gọn: gateway chỉ chờ ~2,5 giây sau khi trang tải rồi đọc các thẻ `<a>` tới `/thread/<id>` đang có trong DOM; thread nằm ngoài vùng tải lười sẽ không được liệt kê cho tới khi sidebar tải đủ.
- (Đã đổi từ v0.7.0, xem điểm 4 ở trên) Session đã xóa khỏi extension nhưng mapping gateway còn thì thread đó sẽ bị coi là đã có và không nhập lại — từ v0.7.0 syncFromWeb không khử trùng theo mapping gateway nữa nên session đã xóa nhập lại được bình thường.
- Cần Chromium + tài khoản đang đăng nhập tốt: gateway mở page tạm trong đúng context của tài khoản để đọc sidebar; cookie hết hạn thì đồng bộ báo hết hạn, không trả danh sách rỗng.
- Đồng bộ theo từng tài khoản, không lẫn tài khoản; đồng bộ không tự chạy nền, không tự xóa session nào, không đổi tài khoản của session cũ.
- Panel Nhật ký chỉ là cửa sổ xem 1000 dòng gần nhất, lịch sử đầy đủ vẫn ở Output > Muse Gateway; panel log không thay thế Output channel. Nội dung panel là đúng những gì đã có trong OutputChannel (cùng máy, cùng user), gateway không in cookie; dòng nào có dạng gán cookie/key/token thì extension che giá trị trước khi đưa vào buffer, và panel không bao giờ ghi nội dung request, cookie hay key. Diagnostic nội bộ của driver (BrowserDriver.Diagnostic) hiện không được gateway app subscribe nên không hiện trong panel — panel chỉ hiện những gì gateway in ra stdout/stderr cộng với lỗi phía extension.

Panel còn có mục cấu hình Muse hiển thị chỉ đọc (autoApprove, gatewayMode, baseUrl, model...) kèm nút mở Settings UI của VS Code để sửa thật. Khung chat chỉ giữ bubble lỗi đăng nhập với nút "Mở Cài đặt".
2. **Quản lý session kiểu navigation drawer.** Header khung chat có nút "☰ Quản lý hội thoại" + tiêu đề session hiện tại + nút "Cài đặt". Drawer là panel thu gọn/mở được ngay dưới header (không dùng overlay phức tạp trong sidebar): đóng thì chỉ thấy header + chat, mở thì hiện menu + danh sách. Menu đúng 4 nút: "Hội thoại mới", "Đổi tên", "Xóa hội thoại", "Quản lý hội thoại" (ba nút đầu tác động ngay session hiện tại, nút cuối bật/tắt phần danh sách). Bấm item trong danh sách thì đóng drawer và mở lại chat của session đó. Các lệnh palette session vẫn giữ nguyên.
3. **Danh sách hội thoại và tài khoản gắn với session (chuẩn bị multi-account).** Mỗi session giờ lưu thêm accountId/accountLabel (và trạng thái lúc lưu). Khi tạo session mới, extension thử lấy danh sách tài khoản (best effort, không chặn nếu gateway chưa chạy); nếu pool có đúng 1 tài khoản thì ghi tài khoản đó, nếu có 0 hoặc nhiều tài khoản thì để trống (chưa xác định) — tuyệt đối không đoán khi có nhiều tài khoản, vì gateway chọn account theo affinity nội bộ và admin API không lộ mapping conversation → account. Session cũ chưa có accountId sẽ được backfill tương tự trong lần làm mới tài khoản, nếu pool có đúng 1 tài khoản. Danh sách hiển thị tiêu đề, số tin, thời gian cập nhật, thư mục (nếu có) và tài khoản (nhãn, hoặc "Chưa xác định tài khoản").
4. **Trạng thái từng hội thoại trên danh sách.** Đúng 3 giá trị: **Đang chạy** = session hiện tại đang có yêu cầu chạy; **Đã logout** = session có accountId đã lưu nhưng account đó không còn trong pool hoặc trạng thái Invalid (hết hạn); còn lại là **Đã dừng** (gồm session chưa xác định tài khoản và session có account đang active/cooling/disabled — cooling/disabled chỉ ghi chú riêng trong chi tiết, không thành trạng thái thứ 4). Trạng thái tính từ cache tài khoản mới nhất, làm mới tài khoản xong thì gửi lại danh sách; trạng thái chạy không lưu bền (mở lại VS Code thì không còn Đang chạy).
5. **Mở lại chat và gate đăng nhập lại.** Bấm item thì mở lại chat của session đó; nếu tài khoản của session đó đã logout (kiểm tra lúc chuyển, nếu gateway chạy được) thì hiện bubble cảnh báo nhưng vẫn cho xem lại lịch sử cũ. Ở tin nhắn tiếp theo user nhắn, gate ở đầu run() (sau khi đảm bảo gateway chạy, trước khi gửi chat) kiểm tra tài khoản của session: nếu không còn trong pool hoặc Invalid thì KHÔNG gửi chat, hiện bubble yêu cầu đăng nhập lại với nút "Mở Cài đặt"; nếu đang cooling thì chặn với lý do cooling + nút Mở Cài đặt (để reset); nếu bị tắt thì chặn với lý do đã tắt + nút Mở Cài đặt (để bật lại). Nếu session chưa xác định tài khoản, hoặc không đọc được pool do 401 gateway ngoài (admin key riêng), thì KHÔNG chặn để tránh khóa user. Extension không tự gửi lại yêu cầu sau khi đăng nhập lại; user tự gửi lại tin nhắn.
6. **Quản lý đa tài khoản Muse đầy đủ trong panel Cài đặt.** Danh sách tất cả tài khoản trong pool (GET /admin/accounts); bấm vào từng tài khoản để mở rộng xem chi tiết: id, nhãn, trạng thái, bật/tắt, tạo lúc, dùng lần cuối, success_count, fail_count, cooldown, lỗi cuối, ngày hết hạn cookie sớm nhất (chỉ ngày/giờ, không giá trị cookie — panel không hiển thị cookie kể cả dạng đã che), các session đang dùng tài khoản đó, và quota khi bấm "Xem quota" (quota có thể thất bại khi tài khoản Invalid, panel báo nhẹ). Thao tác từng tài khoản: Làm mới/Renew, Xóa cooldown, Bật/Tắt, Đổi tên nhãn (PATCH label qua input box), Đăng xuất/Xóa khỏi pool (DELETE sau khi xác nhận, xóa bền vững khỏi cả file lưu; các session của tài khoản đó chuyển sang Đã logout, session không bị xóa).
   - **Thêm tài khoản — luồng chính: đăng nhập qua trình duyệt.** Nút "Đăng nhập qua trình duyệt" trong panel Cài đặt: nhập nhãn (mặc định "Tài khoản cá nhân"), gateway mở một cửa sổ Chromium có đầu của chính nó (1200×800, Playwright instance riêng, không dùng chung browser của chat nên không gián đoạn chat đang chạy), bạn đăng nhập trong cửa sổ đó, panel poll trạng thái mỗi 3 giây, thành công thì tự làm mới danh sách và báo tên tài khoản đã lưu. Mở muse.ai trong trình duyệt ngoài rồi đăng nhập thì không truyền được session sang gateway (gateway dùng context riêng, không đọc profile trình duyệt hệ thống) nên không dùng cách đó. Chỉ một phiên đăng nhập chờ tại một thời điểm (mở thêm sẽ lỗi rõ kèm id phiên đang chờ); đóng cửa sổ tay thì phiên bị hủy; hết 10 phút chưa đăng nhập thì phiên hết hạn. Chưa cài Chromium thì gateway lỗi rõ và panel hướng dẫn bấm "Cài Chromium cho gateway".
   - **Gia hạn lại: "Đăng nhập lại qua trình duyệt" trên chi tiết từng tài khoản.** Gọi start với accountId đó; cùng danh tính Muse thì cập nhật tài khoản cũ (giữ nguyên Id, xóa cooling); nếu tài khoản vừa đăng nhập khác với tài khoản cần gia hạn thì panel cảnh báo rõ: đã lưu thành tài khoản mới, tài khoản cũ vẫn còn trong danh sách (không tự xóa tài khoản cũ, không tự nối session cũ sang id mới).
   - **Phương án dự phòng: nhập từ app desktop.** Nút "Nhập đăng nhập từ app desktop": (1) trong app Muse desktop dùng nút "Đăng nhập tài khoản khác" để thêm từng tài khoản, (2) trong panel bấm nhập để đưa toàn bộ danh sách vào pool (panel tự làm mới sau khi nhập, qua ensureStarted). Panel không mở form đăng nhập (VS Code không có WebView2, gateway không nhận username/password, chỉ nhận cookie).

## Giới hạn thật (đọc trước khi dùng v0.5.0)

- Đăng nhập lại đầy đủ khi cookie hết hạn có hai đường: đăng nhập qua trình duyệt trong panel Cài đặt (gateway mở cửa sổ Chromium của chính nó, cần Chromium và cửa sổ có đầu trên Windows), hoặc qua app Muse desktop rồi Nhập đăng nhập — vì VS Code không có WebView2 để đăng nhập trực tiếp trong extension.
- Tài khoản của session chỉ xác định chắc khi pool có đúng 1 tài khoản; khi có nhiều tài khoản, session mới/cũ chưa xác định sẽ để trống cho tới khi pool chỉ còn 1 tài khoản lúc backfill.
- Id tài khoản là ngẫu nhiên (acc_ + chuỗi ngẫu nhiên), không suy ra từ danh tính Muse: xóa một tài khoản rồi nhập lại cùng tài khoản Muse đó sẽ có Id mới, và session cũ ghi Id cũ sẽ không tự nối lại được. Extension không tự nối lại theo nhãn, vì nhãn mặc định ("Tài khoản cá nhân") không duy nhất.
- Lệnh nhập đăng nhập ghi đè toàn bộ danh sách tài khoản của gateway bằng danh sách từ app desktop (có sao lưu .bak-timestamp trước khi ghi): tài khoản nào đang ở gateway mà không có trong app desktop sẽ mất sau khi nhập.
- Session trước 0.3.3 không bao giờ được lưu thành danh sách nên không thể khôi phục thành nhiều session cũ, chỉ lịch sử cuối cùng thành 1 session.

## Mới trong v0.4.0: danh sách session nhìn thấy được + bảng quản lý đăng nhập Muse

- Danh sách session nhìn thấy được: thay dropdown nhỏ bằng danh sách session hiển thị rõ ở đầu khung chat (tiêu đề, số tin, thời gian cập nhật, thư mục), bấm vào session nào là làm việc tiếp session đó. Session lưu toàn cục theo user (globalState) nên mở thư mục khác vẫn thấy đủ danh sách; lần đầu lên 0.4.0 sẽ hợp nhất session từ global + session workspace của 0.3.3 + lịch sử cũ. Lưu ý thật: session trước 0.3.3 không bao giờ được lưu thành danh sách nên không thể hiện thành nhiều session cũ, chỉ lịch sử cuối cùng thành 1 session; session workspace khác tạo ở 0.3.3 sẽ được kéo vào khi bạn mở lại đúng workspace đó một lần. Ngoài khung chat, session còn quản lý được từ Command Palette: "Muse: Chọn hội thoại", "Hội thoại mới", "Đổi tên", "Xóa".
- Bảng quản lý đăng nhập Muse trong khung chat ("Tài khoản Muse", ngay dưới danh sách session): luôn hiện trạng thái gateway và từng tài khoản (nhãn, trạng thái active/cooling/invalid, bật/tắt, cooldown, lỗi cuối — không bao giờ hiện cookie). Từ đây bạn tự kiểm tra được có lỗi đăng nhập hay không mà không cần đoán: nếu chưa có tài khoản thì bảng báo rõ và đó là nguyên nhân lỗi 503; nếu Invalid/cooling thì thấy rõ trạng thái và lỗi cuối. Nút theo từng tài khoản: Làm mới / Đăng nhập lại (Renew qua gateway), Xóa cooldown, Bật/Tắt, Đăng xuất (xóa khỏi pool gateway, hỏi xác nhận; không đăng xuất app desktop). Nút chung: Kiểm tra lại tài khoản, Nhập đăng nhập từ app desktop, Mở dashboard, Khởi động lại gateway. Đăng nhập lại đầy đủ khi cookie hết hạn: đăng nhập lại trong app Muse desktop rồi bấm Nhập đăng nhập từ app desktop (VS Code không có WebView2 nên không đăng nhập trực tiếp trong extension được).

## Mới trong v0.3.3: quản lý session + lỗi 502 dạng dễ hiểu

- Quản lý session (trước đây không có giao diện này, chỉ có một lịch sử duy nhất theo workspace): thanh session ở đầu khung chat gồm danh sách chọn hội thoại, nút Hội thoại mới, Đổi tên, Xóa hội thoại. Mỗi session có lịch sử và conversationId riêng (gửi gateway làm ID thread), chuyển session là chuyển cả lịch sử lẫn thread. Lịch sử cũ được chuyển thành session đầu tiên, không mất. Tin đầu tiên của session mới tự đặt tên session. Nút Xóa lịch sử vẫn giữ nghĩa cũ: làm trống hội thoại hiện tại và mở thread mới, session vẫn giữ tên.
- Lỗi 502 upstream: khi Muse web bắt đầu trả lời rồi dừng mà gateway không xác định được phản hồi hoàn tất, extension giờ hiện hướng dẫn tiếng Việt thay vì JSON thô: hội thoại được giữ nguyên, không tự gửi lại, đừng tạo session mới hay xóa lịch sử, hãy gửi tiếp tin ngắn trong cùng session.

### Điều khiển màn hình Windows THỬ NGHIỆM (chỉ Windows, mặc định TẮT)

Đây là phần duy nhất không thể bê nguyên từ app desktop sang VS Code:
app desktop dùng UI Automation và SendInput của project
`Muse2Api.Computer` trên .NET Windows, còn extension host chạy Node
không load được DLL đó và VS Code API không có UI Automation hay chụp
màn hình desktop. Vì vậy v0.3.0 làm theo cách sau, và **không giả vờ**
chạy khi không đủ điều kiện:

- **Helper .NET riêng:** project mới `src/Muse2Api.ComputerHelper`
  (console `net10.0-windows`, tham chiếu `Muse2Api.Computer`, publish
  win-x64 self-contained vào
  `bin/win-x64/computer-helper/Muse2Api.ComputerHelper.exe`), giữ một
  `DesktopComputer` duy nhất và nói chuyện với extension bằng JSON-lines
  qua stdin/stdout. Mọi logic UI Automation, cache element, snapshot
  ảnh cho click đều là code thật của `DesktopComputer`, không viết lại.
- **Bật:** đặt `muse.allowComputerControl` thành `true` (mặc định
  `false`). Khi tắt, không phải Windows, hoặc thiếu helper, mọi tool
  `computer_*` trả lỗi rõ ràng và hướng về app desktop.
- **Chọn cửa sổ đích:** extension hỏi chọn bằng QuickPick từ danh sách
  cửa sổ (`computer_list_windows`), rồi mới chạy các tool khác. Helper
  không tự mở cửa sổ chooser như bản desktop; cách dừng khẩn cấp là
  lệnh “Muse: Dừng điều khiển màn hình” (hủy chọn cửa sổ và tắt helper),
  vì helper không có cửa sổ WinForms để nhận phím Esc như bản desktop.
- **Duyệt riêng từng hành động:** mọi hành động `computer_click`,
  `computer_type`, `computer_key`, `computer_invoke`, `computer_set_value`,
  `computer_toggle`, `computer_select`, `computer_expand`,
  `computer_scroll` đều hiện modal riêng ghi rõ hành động và cửa sổ đích,
  **kể cả khi `muse.autoApprove` bật**. Sau `computer_screenshot`, ảnh
  được đưa vào lượt model tiếp theo dưới dạng `image_url` data URI,
  đúng cách `AgentLoop` của bản desktop làm với `LastComputerImage`.
- **Rủi ro phải biết trước:** hành động này bấm/gõ thật vào Windows.
  Chỉ bật khi bạn đang nhìn thấy đúng cửa sổ đích, và đừng chọn cửa sổ
  VS Code đang chạy extension nếu bạn không muốn model bấm vào chính
  VS Code. Helper chỉ tự loại trừ cửa sổ của chính nó, không loại trừ
  VS Code.
- **Kích thước gói:** helper self-contained khoảng 173 MB chưa nén, cộng
  gateway khoảng 213 MB, nên file `.vsix` v0.3.0 sẽ to hơn hẳn v0.2.0
  (xem dung lượng thực tế khi giao). Repo vẫn không chứa binary: script
  `scripts/Build-VscodeExtension.ps1` nay publish cả helper trước khi
  đóng gói (chỉ trên runtime `win-*`; trên runtime khác thì bỏ qua
  helper và extension báo rõ computer_* không khả dụng).

## Mới trong v0.2.0: gateway kèm theo, tự chạy khi mở VS Code

- **Gateway tự chạy khi mở VS Code.** Extension đóng gói sẵn gateway
  Muse2Api cho Windows x64 (`bin/win-x64/Muse2Api.exe`) và tự khởi động
  nó ngay khi VS Code mở lên (nhờ `onStartupFinished`), kể cả khi bạn
  chưa bấm biểu tượng Muse. Bạn **không còn phải chạy gateway tay** nữa.
  Trạng thái gateway hiện ở thanh trạng thái góc phải dưới
  (“Muse Gateway: Đang chạy / Đang khởi động… / Lỗi”) và log đầy đủ ở
  **Output > Muse Gateway**.
- **Dùng luôn gateway sẵn có nếu đã chạy.** Nếu app Muse desktop hoặc một
  gateway khác đã chạy sẵn ở cùng cổng và key khớp, extension dùng luôn
  gateway đó thay vì khởi động thêm một tiến trình nữa. Gateway ngoài
  đang chạy nhưng key không khớp sẽ **không bị giết** — extension chỉ báo
  lỗi key không khớp, bạn dán đúng key vào `muse.apiKey` là dùng được.
- **Key tự quản lý.** Nếu `muse.apiKey` để trống, key cho gateway kèm
  theo được tự sinh dạng `m2a-…` và lưu trong SecretStorage của VS Code,
  không ghi vào Settings, không in ra log.
- **Lệnh gateway mới** (Command Palette, gõ “Muse:”): Khởi động gateway,
  Dừng gateway kèm theo, Khởi động lại gateway, Nhập đăng nhập từ app
  desktop, Cài Chromium cho gateway, Xem log gateway, Mở dashboard
  gateway.

### Lần đầu chưa có đăng nhập thì làm sao?

Gateway chạy được chưa có nghĩa là đã có tài khoản Muse để gọi. Tài
khoản Muse (cookie phiên) lưu trong `accounts.json` của gateway. Làm
theo một trong hai cách:

1. **Nếu máy đã có app Muse desktop đăng nhập rồi (cách nhanh nhất):**
   chạy lệnh **“Muse: Nhập đăng nhập từ app desktop”**. Lệnh này chỉ
   **copy** file `accounts.json` từ
   `%LOCALAPPDATA%\Muse2Api.WinForms\Gateway\` sang thư mục dữ liệu của
   gateway kèm theo — **không xóa, không sửa dữ liệu của app desktop**.
   Việc này chỉ hoạt động trên **cùng máy, cùng tài khoản Windows**, vì
   cookie được mã hóa DPAPI theo tài khoản đó. Sau khi nhập, dùng lệnh
   “Muse: Khởi động lại gateway” rồi gửi yêu cầu.
2. **Nếu chưa có app desktop đăng nhập:** mở app Muse desktop, đăng nhập
   tài khoản Muse một lần, rồi làm theo cách 1. Hoặc mở dashboard của
   gateway (lệnh “Muse: Mở dashboard gateway”, `http://127.0.0.1:18610/dashboard`)
   để thêm tài khoản theo hướng dẫn trong đó.

### Nếu gateway thoát vì thiếu Chromium thì làm sao?

Gateway dùng driver “browser” nên cần một trình duyệt để mở muse.ai.
Extension ưu tiên Edge/Chrome đã cài sẵn trên máy (truyền qua
`MUSE2API_CHROMIUM_PATH`). Nếu máy không có Edge/Chrome và cũng chưa có
Chromium của Playwright, gateway sẽ thoát ngay khi khởi động và log sẽ
ghi rõ lỗi Playwright. Khi đó, làm một trong hai việc rồi khởi động lại
gateway:

- Chạy lệnh **“Muse: Cài Chromium cho gateway”** một lần (chạy
  `playwright.ps1 install chromium` kèm theo binary), hoặc
- Cài Edge hoặc Chrome rồi dùng lệnh “Muse: Khởi động lại gateway”.

## Cách hoạt động

- Extension là **giao diện chat**, không tự chứa model. Nó gọi gateway
  Muse2Api qua API tương thích OpenAI tại `POST /v1/chat/completions`.
- Sau khi model trả về khối tool (cùng giao thức với agent terminal
  `Muse2Api.Agent`: ```json {"tool_calls": [...]} hoặc ```tool legacy),
  extension tự thực thi tool trong workspace đang mở bằng API của VS Code /
  Node: `list_files`, `read_file`, `read_files`, `search_files`,
  `write_file`, `edit_file`, `run_command` (kể cả `background: true`),
  `process_status`, `process_input`, `process_stop`, `git_status`,
  `git_diff`, và (thử nghiệm, chỉ Windows, khi bật
  `muse.allowComputerControl`) toàn bộ 14 tool `computer_*` qua helper
  .NET riêng.
- Mọi thao tác ghi tệp và chạy lệnh đều **hỏi duyệt trước** (hộp thoại
  modal), riêng sửa/ghi tệp có thêm nút **Xem diff**. Chỉ khi bật
  `muse.autoApprove` mới tự duyệt. Lệnh chạy với quyền của người dùng và
  **không bị sandbox** trong workspace, giống bản desktop.

## Cài đặt

### 1. Gateway: từ v0.2.0 không cần chạy tay nữa

Mặc định, mở VS Code là extension tự chạy gateway kèm theo. Mục này chỉ
còn áp dụng khi bạn muốn dùng gateway ngoài thay vì gateway kèm theo
(đặt `muse.gatewayMode` thành `external`):

```powershell
# Windows (PowerShell), đặt key tùy ý rồi chạy gateway
$env:MUSE2API_API_KEY = "khoa-cua-ban"
$env:MUSE2API_PORT = "18610"
dotnet run --project src/Muse2Api -c Release
```

Hoặc dùng gateway của app desktop đang chạy (mặc định cổng 18610; key
nằm trong file `api_key` dưới thư mục `Gateway` của app desktop, ví dụ
`%LOCALAPPDATA%\Muse2Api.WinForms\Gateway\api_key`).

### 2. Cài extension

- Mở file `.vsix` trong VS Code: bấm phải vào file > **Install Extension
  VSIX**, hoặc chạy `code --install-extension muse-vscode-0.3.0.vsix`.
- Mở một thư mục dự án, bấm biểu tượng **Muse** ở thanh Activity Bar
  (trái), hoặc chạy lệnh **Muse: Mở chat** từ Command Palette.

### 3. Cấu hình (Settings > tìm `muse.`)

- `muse.baseUrl`: mặc định `http://127.0.0.1:18610/v1`.
- `muse.model`: mặc định `muse-chat`.
- `muse.apiKey`: để trống thì extension tự quản lý key cho gateway kèm
  theo; chỉ cần dán key khi dùng gateway ngoài chạy sẵn mà key không khớp.
- `muse.gatewayMode`: `auto` (mặc định), `bundled` hoặc `external`.
- `muse.gatewayPath`: để trống thì dùng binary kèm theo extension.
- `muse.maxSteps`: mặc định 30 bước tool / yêu cầu.
- `muse.commandTimeoutSeconds`: mặc định 120 giây / lệnh.
- `muse.autoApprove`: mặc định `false` (khuyên giữ nguyên).
- `muse.allowComputerControl`: mặc định `false` (thử nghiệm, chỉ Windows).
- `muse.computerHelperPath`: để trống thì dùng helper kèm theo extension.

## Phát triển (build từ source trong repo này)

Lưu ý quan trọng: thư mục `bin/` bị gitignore nên **repo không chứa
binary gateway**. File `.vsix` đã giao cho bạn thì có kèm binary, còn
khi build từ repo thì phải publish gateway trước rồi mới đóng gói
extension. Trên Windows, chạy một lệnh duy nhất từ gốc repo:

```powershell
.\scripts\Build-VscodeExtension.ps1
```

Lệnh này publish `src/Muse2Api` cho `win-x64` vào
`vscode-extension/bin/win-x64/`, rồi chạy `npm install`, `npm run compile`
và `npx vsce package` để ra file `.vsix`. Muốn bỏ qua bước publish
gateway (khi đã có sẵn binary trong `bin/`), thêm `-SkipGateway`.

Build tay trên Linux/macOS (thay `win-x64` bằng runtime của máy, ví dụ
`linux-x64` hoặc `osx-arm64`):

```bash
dotnet publish src/Muse2Api -c Release -r linux-x64 --self-contained true -o vscode-extension/bin/linux-x64
cd vscode-extension
npm install
npm run compile        # ra out/extension.js
node scripts/ensure-extension-icon.js   # khôi phục images/icon.png từ images/icon.png.base64 nếu thiếu, fail-fast nếu không khôi phục được (bắt buộc trước mọi lần đóng gói, xem mục 0.8.14)
npx @vscode/vsce package   # ra file .vsix
```

Bản extension trên nền tảng khác Windows x64 sẽ báo rõ là chưa có binary
kèm theo nếu bạn đóng gói mà không publish gateway cho đúng runtime đó;
khi đó hãy dùng `muse.gatewayMode = "external"` và chạy gateway ngoài.

## Sửa lỗi v0.1.1: không thấy biểu tượng sau khi cài (lỗi của v0.1.0)

Nguyên nhân đã xác minh trong code: ở v0.1.0, `contributes.views` trong
`package.json` bị viết dạng mảng, trong khi VS Code bắt buộc dạng object
theo id của views container, ví dụ `"views": {"muse": [{"id": "muse.chat",
...}]}`. VS Code bỏ qua khai báo sai định dạng đó nên không hiện biểu
tượng ở thanh Activity Bar. v0.1.1 đã sửa đúng định dạng, bỏ `when`

hiện cả khi chưa mở thư mục nào.

## Nếu cài bản mới rồi mà vẫn không thấy biểu tượng, kiểm tra theo thứ tự

1. Gỡ bản cũ rồi cài lại bản 0.1.1, sau đó khởi động lại VS Code hoàn
   toàn (đóng hết cửa sổ, mở lại). Cài đè không gỡ đôi khi giữ lại bản
   cũ trong bộ nhớ.
2. Nhìn thanh dọc ngoài cùng bên trái (Activity Bar): biểu tượng là ô
   vuông tím có chữ M. Bấm vào đó, khung Chat phải hiện ở sidebar.
   Nếu không thấy thanh dọc này, bấm View > Appearance > Activity Bar.
3. Mở Extensions (Ctrl+Shift+X), gõ "Muse": extension phải hiện trạng
   thái Enabled và version 0.1.1. Nếu thấy Disabled thì bấm Enable.
4. Mở Command Palette (Ctrl+Shift+P), gõ "Muse: Mở chat": nếu lệnh

## Sửa lỗi v0.1.2: vẫn không thấy biểu tượng, Runtime Status báo container không tồn tại

v0.1.1 mới sửa được một nửa: sửa `views` sang dạng object, nhưng quên
`viewsContainers` vẫn còn dạng mảng từ bản đầu. Theo tài liệu chính thức
VS Code (Tree View API), cả hai đều phải là object:

- `"viewsContainers": {"activitybar": [{"id": "muse", "title": "Muse",
  "icon": "media/icon.svg"}]}`
- `"views": {"muse": [{"id": "muse.chat", "name": "Chat",
  "type": "webview"}]}`

Vì container `muse` chưa từng được đăng ký đúng nên VS Code báo đúng
như user thấy: "View container 'muse' does not exist and all views
registered to it will be added to 'Explorer'", và extension chưa bao giờ
được kích hoạt (onView:muse.chat không bao giờ xảy ra) nên Runtime
Status hiện "Not yet activated". v0.1.2 sửa cả hai về đúng định dạng
trên. Lần này, trước khi giao, manifest trong file .vsix đã được đọc
lại để đối chiếu từng trường, không chỉ kiểm tra code nguồn.
